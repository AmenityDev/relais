# Changing the API contract

Three artefacts are generated, each diffed in CI. Editing any of them by hand is a
build failure waiting to happen.

```text
Go request/response structs  →  docs/openapi-{admin,public}.json  →  web/src/lib/api.generated.d.ts
internal/db/queries/*.sql    →  internal/db/gen/*.go
```

## The sequence

```sh
# 1. change the Go types / handler / query / migration
task openapi      # regenerate both OpenAPI documents from the Go types
task web:types    # regenerate the frontend types from docs/openapi-admin.json
task generate     # only if you touched internal/db/queries or a migration (needs sqlc)
task lint         # the same freshness checks CI runs
task test:all
```

`task lint` runs `relais openapi -surface admin -check docs/openapi-admin.json` (and
`-surface public`), so a handler whose shape changed without a regeneration fails
locally before it fails in CI. This is the most common oversight in this repository.

## How the generator works

`internal/httpapi/openapi.go` reflects over the **real** DTOs that serve the requests —
nothing is written by hand (F12). Things to know:

- Request schemas are named per operation (`BackendInput` vs `BackendPatch`), because
  create and patch differ and one shared name would describe neither.
- A type with a custom `UnmarshalJSON` cannot be reflected faithfully; those are listed
  in `customSchemas`.
- `info.version` is the **API** version (`v1`), never the build version. A rebuild must
  not change the document.
- A `400` response is derived from the presence of a request body.
- Errors are wrapped: the wire shape is `{"error": {"code": …, "message": …}}`,
  `schemaNames` mapping `errorEnvelope{}` → `Error` and `errorBody{}` → `ErrorDetail`.
  The document once named the inner type, so every API error reached the operator as a
  bare status code, and fifteen anti-drift tests all agreed with each other because they
  compared names derived from the same Go types.
  `TestErrorResponsesMatchTheDocumentedSchema` sends real requests and compares bodies
  to the schema — keep that kind of test when adding to the surface.

## The two surfaces are separate

| Surface | Listener | Routes |
| --- | --- | --- |
| public | `RELAIS_HTTP_ADDR`, `:8080` | `POST /v1/emails`, `GET /v1/emails/{id}` |
| admin | `RELAIS_ADMIN_ADDR`, `:8081` | `/admin/v1/*` |

`/admin/v1` on 8080 answers 404 and vice versa; a test asserts the cross-port 404s.
Adding a route means choosing a surface deliberately, and regenerating that surface's
document.

Admin reads: `identity`, `stats`, `backends`, `domains`, `domains:resolve`,
`credentials`, `credentials/{id}`, `credentials/{id}/patterns`, `messages`,
`messages/{id}`, plus two dry runs open to viewers (`patterns:validate`,
`credentials/{id}/patterns:test`). Everything that writes lives in the
admin-only `Group` — 14 operations a viewer must not be able to perform, which is
covered by a test that also asserts nothing changed in the database.

## Queries and migrations

- `internal/db/queries/*.sql` are sqlc sources; `internal/db/gen` is generated. Use
  `sqlc.narg()` for anything optional — `@name` parameters are non-nullable and
  `WHERE (@filter IS NULL OR …)` silently matches nothing.
- Migrations are goose files embedded via `embed.FS`, numbered sequentially
  (`00001_init.sql`), with `-- +goose Up` / `-- +goose Down` and
  `StatementBegin/StatementEnd` around anything containing semicolons. Migrations are
  never implicit: `relais migrate up` is its own command, and its own container in
  deployment.
- `store` is the only package allowed to touch tables. Validation failures returned from
  it carry `store.ErrValidation` so the HTTP layer can answer 400 without reading error
  text.
- New columns that would only serve bounce handling, templates, tracking or
  multi-tenancy do not belong here — the schema anticipates none of them on purpose.

## The frontend side

`web/src/lib/api.generated.d.ts` is generated by `openapi-typescript@7.13.0`; never edit
it. The typed client in `web/src/lib/server/api.ts` reads `parsed.error.code` — it
depends on the envelope above. Everything under `web/src/lib/server/` is
server-only, enforced at build time by SvelteKit: importing it from client code fails
the build, which is what makes "the browser never holds a token" (F2) mechanical rather
than a matter of discipline. Data reaches pages through `load` and form actions only
(F10).

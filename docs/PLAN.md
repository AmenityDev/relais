# relais — implementation plan

An SMTP/API gateway between internal applications and an outbound SMTP relay (OCI
Email Delivery). relais authenticates senders, strictly validates `From`
addresses, and relays. **It does not handle DKIM**: signing happens downstream, at
the relay.

This document is the reference for the decisions that were taken. It is updated
when a decision changes, not when code is written.

---

## 1. Architecture decisions

| # | Decision | Status |
| --- | --- | --- |
| D1 | Router: **chi**. Standard `net/http` handlers, so stdlib middleware and `otelhttp` compose without an adapter, and the submission logic stays reusable across the REST and SMTP façades | accepted |
| D2 | Sender secrets: **HMAC-SHA256(pepper, secret)** plus an indexed public `lookup`, **not argon2id** | accepted |
| D3 | A **single `lookup` column** for both credential types: one unique index, one query path | accepted |
| D4 | The **header `From` is authoritative**; `MAIL FROM` is rewritten from it | accepted |
| D5 | A **closed pattern grammar** (four shapes), validated on write, matched without regex | accepted |
| D6 | The backend is resolved **at ingestion** and pinned to the message; `domain.include_subdomains` | accepted |
| D7 | The message body lives in `email_payload`, with configurable retention | accepted |
| D8 | `Idempotency-Key` supported from v1 | accepted |
| D9 | **One binary** with subcommands; migrations never implicit | accepted |
| D10 | **goose** (application schema) plus **rivermigrate** (river schema); **sqlc** for data access | accepted |
| D11 | OIDC: Authentik issues a JWT, **Go validates it against the JWKS**; SvelteKit forwards the access token | accepted |
| D12 | Out of scope for v1: bounces/DSN, templates, tracking, multi-tenancy. The schema anticipates **none** of it | accepted |
| D13 | Rate limiting **in-process**, per credential; outbound throughput bounded by `smtp_backend.max_concurrency` | accepted |
| D14 | TLS for the SMTP server: **mounted files** (reloaded on SIGHUP) **or** a **generated self-signed** certificate (tests and development, refused when `RELAIS_ENV=prod`) | accepted |
| D15 | **A separate HTTP listener for the admin API** (`RELAIS_ADMIN_ADDR`, default `:8081`) | accepted |

### D2 — why not argon2id

Two reasons, and the second is the real one:

1. **Latency on the hot path.** A properly calibrated argon2id costs 50–150 ms
   *per REST request* and *per SMTP connection*.
2. **These are not human passwords.** Secrets are generated by relais with 256
   bits of entropy. A slow KDF protects a low-entropy secret against brute force;
   here brute force is impossible whatever the hash function.

The pepper lives **only** in the environment: a stolen SQL dump cannot even *test*
a candidate secret, a guarantee argon2id without a pepper does not offer.

An API key's layout:

```text
relais_sk_<lookup 12><_><secret 43>
           └ base32 ┘   └ base64url ┘
```

The lookup and the secret are drawn **independently**, so publishing the lookup in
the database costs nothing: the secret keeps its 256 bits. Parsing is by fixed
offset rather than by splitting on the separator, because the secret's alphabet
contains `_`.

### D5 — the pattern grammar

| Pattern | Matches | Does not match |
| --- | --- | --- |
| `no-reply@app.example.com` | that exact address | anything else |
| `*@example.com` | any local part, exact domain | `x@mail.example.com` |
| `no-reply@*.example.com` | that local part, any strict subdomain | `no-reply@example.com` |
| `*@*.example.com` | any local part, any strict subdomain | `x@example.com` |

- `*.example.com` does **not** cover `example.com`. Covering both takes two
  patterns: verbose on purpose, so a wildcard never reaches further than what the
  operator wrote.
- `*` is allowed only as an entire local part, or as the leading domain label.
- Domains are normalized to lowercase punycode (IDNA); local parts are compared
  case-insensitively.
- **An empty set matches nothing.** This is the most important property in the
  package: a credential with no pattern can send as nobody.
- The matcher is pure string comparison — no operator input ever reaches a regex
  engine. A database `CHECK` replays the grammar as defence in depth, and a test
  pins the two together so they cannot drift.

## 2. Repository layout

```text
relais/
├── cmd/relais/                 # subcommands: serve, migrate, keygen,
│                               # backend, domain, credential, healthcheck
├── internal/
│   ├── config/                 # env → struct, fail-fast validation
│   ├── obs/                    # slog JSON + OTLP bridge + traces
│   ├── db/
│   │   ├── migrations/         # goose, embedded via embed.FS
│   │   ├── queries/            # sqlc sources
│   │   └── gen/                # generated — never edited by hand
│   ├── crypto/                 # AES-GCM keyring, HMAC+pepper, Secret type
│   ├── tlsconf/                # certificate: mounted files or generated
│   ├── frompattern/            # grammar and matcher (security core)
│   ├── store/                  # the only place that touches the tables
│   ├── mailbuild/              # REST JSON → RFC 5322
│   ├── mailnorm/               # From extraction, missing headers
│   ├── ingest/                 # ⭐ the shared pipeline
│   ├── ratelimit/              # bounded per-credential token buckets
│   ├── sender/                 # SMTP client + 4xx/5xx classification
│   ├── jobs/                   # river workers + transactional Enqueuer
│   ├── authn/                  # credential resolution (bearer and SMTP AUTH)
│   ├── adminauth/              # lazy OIDC/JWKS + admin/viewer RBAC
│   ├── httpapi/                # chi: /v1, /admin/v1, health
│   ├── smtpd/                  # submission server (STARTTLS, post-TLS AUTH)
│   ├── smtptest/               # programmable SMTP sink (tests)
│   ├── oidctest/               # throwaway OIDC issuer (tests)
│   └── dbtest/                 # database access for integration tests
├── web/                        # SvelteKit                        [to come]
├── deploy/Dockerfile           # multi-stage, multi-arch, distroless
├── docker-compose.yaml         # dev: postgres + mailpit
└── Taskfile.yml
```

The contract that holds it all together:

```go
ingest.Service.Submit(ctx, ingest.Request) (ingest.Result, error)
```

Both the REST and SMTP façades build one of these `Request` values and have **no**
other route to the database or the queue. The validation cannot be duplicated by
accident: there is exactly one implementation, with exactly one set of callers.

**The backend is complete.** `serve` exposes the REST API, the submission server,
the admin API on its own port, the health probes and the workers. Only the
frontend is left, and its design is settled in [FRONTEND.md](FRONTEND.md).

One operational decision worth remembering: **OIDC discovery is lazy**. It happens
on the first admin request rather than at startup, and a failure is remembered for
a few seconds instead of being retried on every request. An Authentik outage
therefore never stops relais from relaying mail — it only makes the admin UI
unavailable, with a `503` rather than a `401`.

### Integration tests

The database-backed packages resolve their connection through `internal/dbtest`:

- `RELAIS_TEST_DB_URL` set → the database is **mandatory**, and an unreachable one
  **fails** the test. This is the CI mode: a silently skipped integration suite is
  indistinguishable from a passing one.
- unset → the development stack is tried, and tests skip if it is not running, so
  `go test ./...` does not require Docker.
- A Postgres advisory lock serializes these tests. `go test ./...` runs packages
  **in parallel** and they truncate the same database; without the lock they wipe
  each other mid-run (observed: deadlocks and vanishing rows). `-p 1` would work
  too, but nobody remembers a flag.

`task test` skips when the database is absent; `task test:all` requires it. CI sets
`RELAIS_TEST_DB_URL`, so an unreachable service container fails the run rather than
producing a green build that tested none of the pipeline.

Four packages deliberately have no tests of their own: `db` (pool and migration
runner, exercised by every database-backed test), `obs` (telemetry wiring), and
`dbtest`/`smtptest` which *are* test tooling.

### Verified against a real Postgres 18

- migrations up/down/up, idempotent (application schema plus 7 river migrations)
- backend password sealed (`v1:<key id>:…`) with **no** trace of the plaintext in
  the database
- a full key rotation *including its failure mode* (a stranded row is named
  precisely)
- IDNA normalization (`Exemplé.COM` → `xn--exempl-gva.com`)
- domain resolution with and without `include_subdomains`, most specific row
  winning
- `octet_length(secret_hmac) = 32`, and no secret recoverable
- patterns: idempotent add, removal, refusal of anything outside the grammar
- `serve`: `/healthz`, `/readyz`, `healthcheck`, graceful shutdown, harmless SIGHUP
- the `ingest` pipeline: an accepted message produces a `queued` row, a payload and
  a job **in one transaction** (proved by a failing enqueuer: no row survives)
- a `From` outside the allow-list → a `rejected` row with the attempted address and
  the client IP, no job, no retained content
- a credential with no pattern can send as nobody
- `Bcc` removed from the relayed bytes, kept in the database for the audit trail
- MIME body byte-identical after normalization (quoted-printable, base64, 8bit,
  multipart, long lines)
- idempotency: a replay returns the same id and enqueues one job; keys are scoped
  per credential
- **end-to-end delivery**: submission → river → SMTP → mailpit, status `sent`,
  `relay_response` retained ("queued as 4I5rmXa8y4l3H2VLOtT7sU")
- classification: 4xx retried with backoff, 5xx `failed` without retry
- refusal to send AUTH over an unencrypted connection, checked against the live
  connection state rather than the configuration
- an untrusted certificate fails rather than silently downgrading
- partial delivery → `sent` plus `partial_recipients`, refused addresses named
- the worker is idempotent: a replayed job does not send the message again
- exhausted retries → `failed` (otherwise the row would stay `queued` forever)
- retention: the payload is purged, the message row is kept
- **REST API**: `curl` → 202 → delivery → `GET` reports `sent` with `sent_at`
- every authentication failure returns an **identical** response (no oracle
  distinguishing an unknown key, a revoked one, or a wrong secret)
- one credential cannot read another's messages (404, not 403)
- the access log attributes a request to a credential while never containing the
  subject, the body or the key
- **SMTP façade**: `AUTH` is not even advertised in the clear; `MAIL FROM` without
  authentication → `530`; a full send from a real Python client → delivered to
  mailpit
- the header `From` is authoritative: a diverging `MAIL FROM` is accepted, a
  spoofed `From` is refused `550 5.7.1` and recorded with the attempted address
- `RSET` keeps the authentication; several messages per connection
- a body line starting with a dot survives (dot-stuffing)
- the success reply carries the id: `250 2.0.0 OK: queued as <uuid>`
- **admin API**: JWT signatures verified against a real JWKS; a forged, expired,
  wrong-issuer or wrong-audience token all return `401` with an **identical** body
- an unrecognised group → `403` (not `401`); group matching is case-insensitive; a
  scalar `groups` claim is accepted
- a `viewer` can perform **none** of the 12 writes, and nothing changes in the
  database
- no response carries a sealed password, a fingerprint, or a message body
- the two HTTP surfaces are genuinely separate: cross-port `404`s
- a refused write is logged with the identity that attempted it

## 4. Notes for what follows

- **go-smtp is pre-1.0**: its auth API changed between minor versions
  (`AuthPlain` → `sasl.Server`), and it manages its own connection deadlines,
  clearing any that the caller sets. The version is pinned and the implementation
  is isolated in `internal/smtpd` and `internal/sender` to absorb the breakage.
- **Do not re-encode inbound MIME.** A parse-and-reserialise round trip can break
  legacy messages. Missing headers (`Message-ID`, `Date`) are injected on the raw
  stream; the full parse only serves to extract the `From` and validate.
- **Recipients per message**: OCI caps them. `RELAIS_LIMITS_MAX_RECIPIENTS`
  (default 50) refuses explicitly rather than letting an opaque 5xx arrive three
  seconds later.
- **No email content in the logs, ever.** A validation rejection logs
  `credential_id`, `credential_name`, `from_attempted`, `patterns_count`,
  `remote_ip`, `facade` and `message_id`. Nothing more. The subject is stored in
  the database (useful to an operator) but **never** logged.
- **The pepper is not rotatable** without re-issuing every credential. The keyring
  is (`relais backend rewrap`). Documented in `.env.example`.
- **sqlc's `@name` parameters are non-nullable.** An optional filter written as
  `WHERE (@filter IS NULL OR …)` never takes the IS NULL branch, so the filter
  silently matches nothing. Use `sqlc.narg()` for anything optional; this cost the
  message listing a silent "always empty" bug until an integration test caught it.
- **Never classify an error by its text.** An earlier version of the admin API
  guessed 4xx versus 5xx from substrings and answered `503` to a perfectly valid
  refusal, because "refusing SMTP AUTH over a plaintext backend connection"
  contains the word "connection". Validation failures now carry
  `store.ErrValidation`.
